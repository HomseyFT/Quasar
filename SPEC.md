# quasar — eBPF container security monitor

Watches every process execution and outbound connection across a Docker host,
attributes each to the container that caused it, compares against a reviewed
per-container policy, and alerts on anything unbaselined. Later, blocks it.

Probes in restricted C compiled to BPF with CO-RE. Loader and daemon in Rust.

## Why this project

It merges the three things this tree is otherwise missing a combination of:
kernel-level systems programming, security, and the homelab that is already
running. It also produces code that runs *inside* the kernel under a verifier,
which is an unusual constraint to have worked under.

The concrete motivation: `cloudflared` publishes forgejo, three Django apps and
a dashboard to the internet. The realistic failure is one of those getting RCE.
What that looks like from the kernel is a container that has never run a shell
suddenly running one, then opening a connection it has never opened.

## Target environment

Development happens on Fedora 42 / kernel 6.19. **Deployment target is a
different machine** and its constraints govern every decision here.

| | |
|---|---|
| Host | `nathanwebserver`, Ubuntu 24.04.4 LTS |
| Kernel | 6.8.0-139-generic, x86_64 |
| Resources | 8 CPU, 7.7 GB RAM |
| Containers | 25 running (traefik, cloudflared, forgejo, jellyfin, ollama, pihole, 2× mysql, postgres, 5 nginx, 4 Django backends, portainer, dozzle, uptime-kuma, navidrome) |
| BTF | present, plus 154 module blobs — CO-RE works |
| Ring buffer | available (6.8 ≫ 5.8) |
| fentry/fexit | available (6.8 ≫ 5.5) |
| cgroups | v2 unified, Docker cgroup driver `systemd`, overlay2 |
| BPF LSM | `CONFIG_BPF_LSM=y` but **not in the active LSM list** |
| Toolchain on target | `bpftool` yes, **clang no**, docker yes |
| Hardening | `unprivileged_bpf_disabled=2`, `perf_event_paranoid=4`, `kptr_restrict=2` |

Full report: `scripts/target-report.txt`. Regenerate with
`scripts/probe-target.sh` after any server kernel upgrade.

Three consequences that shape everything:

**No compiler on the target, and glibc skew.** Fedora 42 is glibc 2.41, Ubuntu
24.04 is 2.39 — a dynamically linked binary built here will not run there. The
build produces one statically linked musl binary carrying the BPF objects
embedded. Nothing is compiled on the server.

**7.7 GB across 25 containers means overhead is a budget.** `pihole` alone
generates thousands of `udp_sendmsg` calls per second. Filtering has to happen
in the kernel, not in userspace.

**BPF LSM needs a reboot.** Enforcement is blocked on appending `,bpf` to the
kernel cmdline and rebooting the server. Plan it; do not discover it in phase 5.

## Goals

- Every exec and every outbound connection, attributed to a container, at an
  overhead the host does not notice.
- A policy per container that is a reviewed file in git, not a hidden model.
- Alerts that reach a phone.
- Optional, carefully-gated prevention.

## Non-goals

| Excluded | Why |
|---|---|
| Broad syscall telemetry with learned anomaly scores | Event volume the box cannot afford, an unwinnable false-positive problem, and the project becomes statistics instead of kernel work. |
| A web dashboard | Would be the fourth Django app in this tree and teaches nothing new. It also puts a public web surface on security telemetry. |
| File integrity monitoring | Container filesystems are ephemeral and rebuilt on deploy; the signal is weak. |
| Pure-Rust kernel-side probes | `aya-ebpf` needs rustup nightly and bpf-linker, and verifier errors on Rust-generated bytecode have no matching prior art to search for. |

## Toolchain

**Kernel side.** Restricted C, clang 20, `-target bpf`, CO-RE via
`vmlinux.h` generated by `bpftool btf dump file /sys/kernel/btf/vmlinux format c`.
This is the dialect all kernel documentation, `libbpf-tools` and every bcc
example is written in, so reference material applies without translation.

**Userspace.** Rust 1.95 with `aya` — pure Rust, no libbpf, no libelf, no zlib.
That is what makes `--target x86_64-unknown-linux-musl` produce a single static
binary with no build container.

| Crate | Role |
|---|---|
| `aya` | BPF object loading, CO-RE relocation, map and ringbuf access |
| `tokio` | Async runtime for the ringbuf consumer and the socket server |
| `ratatui` + `crossterm` | The `quasar top` client |
| `serde` + `toml` + `serde_json` | Policy files, JSONL output |
| `bollard` | Docker API client, pointed at docker-socket-proxy |

## Architecture

```
bpf/
  vmlinux.h            generated, committed
  common.h             shared event structs — must match src/event.rs exactly
  exec.bpf.c           tracepoint sched/sched_process_exec
  connect.bpf.c        fentry tcp_v4_connect, tcp_v6_connect, udp_sendmsg
  lsm.bpf.c            bpf_lsm_bprm_check_security          (phase 6)

src/
  main.rs              CLI: run | top | learn | enforce | policy
  loader.rs            aya loading, attach, custom-BTF support
  event.rs             the userspace mirror of common.h
  registry.rs          cgroup id -> container name, the core of the project
  policy/
    mod.rs             policy model, MANUAL vs LEARNED precedence
    sync.rs            push the allowlist down into BPF maps
    learn.rs           observation -> draft TOML
  sink/
    jsonl.rs           the durable event log
    ntfy.rs            alert push
    socket.rs          unix socket server for `quasar top`
  tui.rs               the client
```

### Kernel-side filtering is the load-bearing decision

Userspace never sees a known-good event. The policy is pushed *down* into BPF
maps, and the probe drops matching events before they ever reach the ring
buffer.

```c
struct { __uint(type, BPF_MAP_TYPE_HASH);
         __type(key, struct exec_key);      // { u64 cgroup_id; u8 path_hash[16]; }
         __type(value, u8);
         __uint(max_entries, 16384); } exec_allow SEC(".maps");

struct { __uint(type, BPF_MAP_TYPE_LPM_TRIE);
         __type(key, struct cidr_key);      // { u32 prefixlen; u64 cgroup_id; u32 addr; }
         __type(value, u8);
         __uint(max_entries, 8192);
         __uint(map_flags, BPF_F_NO_PREALLOC); } egress_allow SEC(".maps");
```

`LPM_TRIE` is the right structure for CIDR allowlists — it does longest-prefix
matching in the kernel, so `10.0.0.0/8` is one entry rather than sixteen million.

This is what makes pihole affordable: its DNS traffic matches an allowlist entry
and dies in the probe. It is also exactly the machinery phase 6 needs, so
enforcement becomes a return value change rather than new infrastructure.

A per-cgroup token bucket caps events per container per second, so a container
in a crash-loop cannot flood the ring buffer or the log.

### The attribution registry

The chain from kernel event to a name a human recognises:

```
bpf_get_current_cgroup_id()  ->  u64 (the cgroup dir's inode number)
       |
       |  walk /sys/fs/cgroup, stat() each dir, match st_ino
       v
/sys/fs/cgroup/system.slice/docker-3f9a...b1.scope
       |
       |  parse the 64-hex container id out of the dir name
       v
3f9a...b1
       |
       |  docker-socket-proxy, cached, invalidated by docker events
       v
"marist-backend"
```

The Docker cgroup driver is `systemd`, which is what makes the directory name
carry the container id. Under the `cgroupfs` driver the layout differs; the
registry detects which is in use rather than assuming.

Three fallbacks, in order, because the race is real — a container can exec
before userspace has learned it exists, and a short-lived container's cgroup is
gone before the lookup runs:

1. Registry cache hit.
2. Read `/proc/<pid>/cgroup`, if the process still exists.
3. Report `cgroup:<id>` and mark the event `unattributed`.

Never drop an event for lack of a name. An unattributed exec is still a signal,
and it is the *interesting* one if something is deliberately short-lived.

### Policy model

One TOML file per container, in git, following the rule Finance already uses:
every entry records why it exists, and automated passes never overwrite a manual
one.

```toml
# policy/marist-backend.toml
[meta]
image = "infra-marist-backend"
learned_from = "2026-09-14/2026-09-21"

[exec]
allow = [
  { path = "/usr/local/bin/python3.12", source = "learned" },
  { path = "/usr/local/bin/gunicorn",   source = "learned" },
  { path = "/bin/sh", source = "manual", note = "entrypoint only, see Dockerfile CMD" },
]

[egress]
allow = [
  { cidr = "172.18.0.0/16", source = "manual", note = "compose network" },
  { cidr = "10.0.0.0/8",    source = "manual", note = "LAN + tailscale" },
]
```

`quasar learn` re-run against an existing file adds new `learned` entries and
leaves every `manual` entry untouched — including manual *denials*. A deploy is
followed by `git diff policy/`, which is the entire review process.

## Phases

### Phase 1 — exec events, no attribution

One probe on `sched/sched_process_exec`, a ring buffer, and a loader that prints
raw events. Proves the whole toolchain end to end: clang → BPF object → aya →
CO-RE relocation → attach → ringbuf → stdout.

**Accepts when:** `docker exec -it jellyfin sh` produces an event locally, and
the same binary produces events on the server without recompilation.

### Phase 2 — the registry

cgroup id resolution, the docker-socket-proxy client, the cache, the invalidation
on docker events, and all three fallbacks.

**Accepts when:** every event names a container; killing and recreating a
container does not produce stale names; and a container that execs within 100 ms
of starting is still attributed (test it deliberately).

### Phase 3 — egress

`fentry` on `tcp_v4_connect`, `tcp_v6_connect`, `udp_sendmsg` and
`udpv6_sendmsg`. fentry rather than kprobe: lower overhead, and 6.8 supports it.
`udp_sendmsg` is the AF_INET path only, so v6 datagrams need the second hook or
"both v4 and v6" is only true of TCP.

**These record connection *attempts*, not completed connections.** fentry runs
at function entry, before the handshake, so a refused or timed-out connection
produces an event exactly like a successful one. That is the deliberate choice:
the exfiltration attempt that failed is the one worth alerting on, and a monitor
that only saw successes could be evaded by a peer that never answers. It follows
that "connections" in the policy model means "attempts", and counts will exceed
what netstat or a firewall log reports.

Because fentry runs before the kernel validates its own arguments, each probe
repeats the kernel's `addr_len` and `sa_family` checks. Skipping them would
report a junk destination for any malformed `sendmsg` the kernel is about to
reject -- a false positive that phase 4 would score as real egress.

**Accepts when:** connections are captured with correct destination address and
port on both v4 and v6, for TCP and UDP, and measured overhead on the server
stays under 2% CPU with pihole running.

### Phase 4 — policy, learn mode, alerting

The policy model, the map sync, `quasar learn`, JSONL output, ntfy alerts.
Kernel-side filtering lands here, which is also what makes the volume tractable.

**Accepts when:** a week of `learn` produces policy files for all 25 containers
that you can read and correct; after loading them, a normal day produces zero
alerts; and `docker exec marist-backend sh` fires an ntfy notification.

### Phase 5 — `quasar top`

The unix socket server and the ratatui client. Per-container counters, a live
event tail, alert highlighting.

**Accepts when:** the daemon runs headless with no client attached, and attaching
or killing a client never affects it.

### Phase 6 — enforcement

Requires the server reboot. Append `,bpf` to `GRUB_CMDLINE_LINUX` in
`/etc/default/grub`:

```
lsm=lockdown,capability,landlock,yama,apparmor,bpf
```

then `update-grub` and reboot. Verify with `grep bpf /sys/kernel/security/lsm`.

Attach `bpf_lsm_bprm_check_security`, return `-EPERM` for a disallowed exec.
Two mandatory safety rails:

- **Dry run first, for a full week.** Logs `WOULD BLOCK` and changes nothing.
  A cron job you forgot about will appear here; that is the point.
- **Deadman switch.** More than N blocks in M seconds auto-disarms enforcement
  and fires an alert. `--revert-after <duration>` disarms on a timer regardless.

Arm per-container, starting with something you can afford to break. Not forgejo,
not traefik, not cloudflared.

**Accepts when:** a disallowed exec fails with EPERM and the container survives;
the deadman switch is verified by deliberately tripping it; and disarming
restores normal operation without a restart.

## Testing

**Unit.** Policy precedence (manual beats learned), cgroup path parsing for both
Docker cgroup drivers, LPM key encoding, the token bucket. No root.

**Struct parity.** `bpf/common.h` and `src/event.rs` describe the same bytes in
two languages, and a mismatch silently corrupts every event. A test asserts size
and field offsets match. This is the highest-value test in the project.

**CO-RE relocation against the target.** The server's `vmlinux` BTF blob is
committed under `testdata/btf/`. A test loads every BPF object against that BTF
specifically, so relocation failures against kernel 6.8 surface in CI rather
than on deploy.

```rust
#[test]
fn relocates_against_target_kernel() {
    let btf = Btf::parse_file("testdata/btf/ubuntu-6.8.0-139", Endianness::default())?;
    EbpfLoader::new().btf(Some(&btf)).load(EXEC_OBJ)?;
}
```

Refresh the blob whenever the server's kernel updates — add it to the same
checklist as `probe-target.sh`.

**Integration.** Gated behind `QUASAR_TEST_ROOT=1`. Spins up throwaway
containers locally, execs known binaries, asserts the events appear with correct
attribution.

**Overhead.** A benchmark that measures CPU and event-drop rate under synthetic
load, run before every deploy. Regression here is a bug, not a tradeoff.

## Deployment

Static musl binary + a systemd unit. Runs as root — `unprivileged_bpf_disabled=2`
on the target rules out anything less, and `perf_event_paranoid=4` is stricter
still.

```
make build     # cargo build --release --target x86_64-unknown-linux-musl
make deploy    # scp binary + policy/, systemctl restart quasar
```

Policy files deploy with the binary. The service must start cleanly with no
policy at all (observe everything, alert on nothing) so a bad policy file can
never prevent startup.

## Risks

**The verifier will reject things for opaque reasons.** Budget real time for it.
Keep programs small, avoid unbounded loops, prefer `bpf_probe_read_kernel` over
direct dereferences, and read the full verifier log rather than the last line —
the useful information is usually 40 lines up.

**Struct layout drift between `common.h` and `event.rs`.** Silent, total
corruption. The parity test is non-optional and should exist before the second
probe is written.

**Event volume from pihole and ollama.** If kernel-side filtering slips to a
later phase, phase 3 will appear to work locally and drown on the server. Do not
reorder it.

**Enforcement on infrastructure you depend on.** The dry-run week and the
deadman switch are not optional polish. The failure mode is forgejo not starting
at 2am and the fix requiring the box you cannot reach.

**Scope drift toward Falco.** Falco and Tracee already exist and are large. The
value here is the narrow, well-attributed signal for one specific stack, and a
policy you can read. More probe types is not more value.
